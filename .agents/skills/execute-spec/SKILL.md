# Execute a prepared specification

Read [the execution protocol](references/execution.md) for commands, state, and review JSON. This skill coordinates the whole local loop; the user should not need to invoke review-change separately. It does not merge, push, publish a PR, or release.

1. Run `node tools/execution/task.mjs gate` in the source checkout. On failure, list the blocking changes and stop. Never stash, commit, ignore, or copy those changes to bypass the gate. Start with `node tools/execution/task.mjs start <task-slug>`, or use `resume <task-slug> <run-id>` for an existing run. Markdown and dotfile changes (including dot-directory contents) are excluded by the gate; captured planning inputs must still match their snapshots. Other source changes must remain in the execution worktree. Only one run may be active.
2. Read the run's captured original, prepared spec, planning feedback, and state. Work only in the returned worktree. Implement the requested behavior and meaningful tests; use a failing regression test first when it can demonstrate the behavior. Do not change the spec to fit the implementation. A faulty assumption that changes scope returns to planning: record it in the handoff, stop the run with a reason, and present concrete options.
3. Commit implementation changes locally in the execution worktree. Run `verify <task-slug> <run-id>` from the source checkout. If formatting changes code, review its diff, commit it, and verify again. Inspect logs: formatting may be a no-op for languages without configured formatters. Required checks include the full suite, native UI path, build, and both Qlty checks. Existing failures remain explicit failures; do not silently waive them or weaken checks. If environmental checks cannot run, record unavailable evidence and leave execution incomplete.
4. Collect criterion-specific evidence in the run directory and maintain evidence.md. Desktop checks run serially through verification, which supplies an isolated preferences home and temporary directory; native/document tests already inject fixture recovery stores. For additional interaction checks use disposable fixture documents and a test host with equivalent isolated state, never the user's working documents or their normal running Margin instance. If safe automation is unavailable, report the criterion unavailable rather than claim success. Screenshots support appearance; they do not prove persistence, clipboard, or undo behavior.
5. Delegate review to a fresh session/subagent using the repository's review-change skill (no inherited conversation when supported). Give it the run path, source root, worktree, and relevant instructions; let it inspect original intent, spec, diff, and evidence independently. If no independent session is available, leave the run incomplete and provide a review prompt. Record the returned JSON with `review <task-slug> <run-id> <report-file>`.
6. Fix findings in the worktree, commit, reverify, and request fresh review. Retain prior reviews and explicitly resolve their findings. Allow at most three review rounds; if the third still requests changes, stop incomplete. Stop earlier if repeated failures show no useful progress. Any code change invalidates earlier verification and review.
7. Complete handoff.md with delivered behavior, each criterion's evidence, limitations, and encountered problems/proposed workflow improvements. Do not modify the harness automatically as part of delivering a feature. Run `finish <task-slug> <run-id>` and report ready for user review only if it succeeds. Keep the worktree and branch for inspection; do not automatically merge or remove them.

Send concise progress updates at stage changes, especially verification results, review findings, and stopped runs. Reference concrete artifacts in the final handoff.
