# Resolve all eight current Qlty code smells

## Original intent

There are multiple Qlty code smells; make a proposal to fix each one.

## Proposed behavior

Create a behavior-preserving refactoring plan for every finding in the current default `qlty smells --all` scan. This task is a proposal, not authorization to implement the refactors. The baseline below was captured on 2026-11-02 with Qlty 0.665.0 using both plain output and SARIF. Tests are excluded by the default scan; no duplication finding was reported. Counts are Qlty complexity measures, not line counts or a count of defects.

The targets are strictly below the SARIF thresholds to avoid edge ambiguity. Extract cohesive responsibilities with explicit ownership; whole-program complexity need not fall simply because file complexity falls. Do not suppress findings, change thresholds, exclude moved files, or transfer the same smell into a new oversized module. Proposed filenames describe responsibility and may be adjusted during preparation; final boundaries must be checked with Qlty after each slice.

### S-1: Separate window hosting from sidebar/workspace coordination

Keep EditorWindowController's ordered documents, current document, add/select/remove/move operations, close confirmation, responder forwarding, and content hosting in EditorWindow.swift. Extract the sidebar callback wiring, collapse/resize observations, sidebar-state application, folder scanning, and scan-generation rejection into an owned WindowSidebarCoordinator in a new file. Its lifetime is the host window's lifetime; callbacks hold the host weakly, observer tokens are removed on teardown, and all UI work remains on the current main-thread path. Keep the workspace URL/tree as one owned state rather than mirrored copies. Give the host narrow methods for applying scan results and reading ordered open documents.

If that split still leaves either file at 50 or more, extract the existing restoration encoding/decoding and EditorWindowRestoration adapter into WindowRestoration.swift using an explicit snapshot of document entries, selected index, and workspace. Preserve all current NSCoder keys, secure allowed classes, serial reopen order, recovery metadata, selected-document fallback, and welcome handling. This fallback is part of the proposal, not an arbitrary line-based split. Primary risks are cancelling a multi-document close, stale async scans reaching a changed workspace, and retained window observers.

### S-2: Split the native application by existing types, then extract remaining responsibilities

Margin.swift currently contains MarkdownDocument, asset handling, the weak script-message bridge, several NSView/WKWebView subclasses, DocumentEditor, DocumentController, AppDelegate, and the application entry point. First move existing declarations intact: MarkdownDocument.swift (plus DiskVersion), EditorWebView.swift (web view, container, titlebar drag view), AssetHandler.swift, DocumentEditor.swift (plus MessageBridge), DocumentController.swift, and AppDelegate.swift. Leave the entry point in Margin.swift and place shared notification/type declarations with their owning domain. Preserve runtime Swift module/type names and Info.plist document-class resolution.

Measure each resulting file. Move menu construction into AppMenuBuilder.swift and workspace create/rename/quick-open item collection into WorkspaceActions.swift, leaving AppDelegate's target/action methods as thin forwarders. Keep the AppKit document-open queue inside DocumentController. If DocumentEditor remains above threshold, extract payload decoding/routing into EditorMessageRouter.swift and failure/fallback presentation into EditorFailurePresenter.swift. The router must still reject subframe messages, closed-document callbacks, stale load tokens, and obsolete revisions before accepting edits. Keep EditorSession as the existing authority; do not duplicate it in a router.

If MarkdownDocument remains above threshold, extract its disk-change/conflict decision logic into an owned DocumentDiskMonitor, preserving asynchronous checks, dirty-document protection, Save As behavior, and overwrite confirmation. Keep NSDocument overrides, undo/change-count ownership, and synchronized-save ordering in MarkdownDocument. Keep recovery scheduling/removal paired with the document's lifecycle; extract a recovery helper only if measurement requires it and cancellation semantics remain explicit. Risks are save/undo/recovery ordering, startup-versus-restoration races, bridge lifetime, and accidental access-control widening. New collaborators should receive narrow operations/state, not make all private fields internal to permit cross-file extensions.

### S-3: Separate sidebar state/tree modeling, row presentation, and interactions

Move OpenFileEntry, HeadingEntry, SidebarMode, SidebarState, SidebarNode, and the sidebar-state notification to SidebarModel.swift. Extract the pure filtered-tree/root construction from reloadFiles/tree into a SidebarTreeBuilder operating on folder entries, open-file entries, and the normalized query. Keep AppKit expand/collapse application, syncingTree protection, appliedTree cache, and the rename-in-progress guard with the controller; building a model must not trigger notifications or mutate expansion preferences.

Move SidebarRowView and row/icon/name/cell construction into SidebarRowFactory.swift. If the controller remains above threshold, extract contextual-menu item construction and rename-session handling into a SidebarFileActions collaborator, keeping delegate entry points and callback ownership explicit. Preserve dragged-open-file ordering, Option-collapse semantics, expansion of descendants inside collapsed folders, current-file selection, deferred refresh during rename, cancellation, and filename-without-extension selection. Suggested split: model/tree, row presentation, file actions, and the controller, all individually below 50. Avoid multiple independent stores of filter or toggled-folder state.

### S-4: Turn app.js into a composition root for editor features

Introduce small factory modules in the existing locally loaded classic-script architecture: editor-syntax.js for front matter, Markdown support and highlighting; editor-input.js for image paste/drop, link hit testing, and input handlers; document-session.js for native/browser transport, raw text, tokens/revisions, loading, metadata, and minimal text replacement; editor-formatting.js for formatting commands/dialogs; editor-search.js for find/replace/go-to-line state and UI; document-output.js for HTML export/print and document summaries/outline helpers; and app-controls.js for toolbar/popover/keyboard bindings. Keep app.js responsible for assembling the editor and publishing the existing window.app API.

Each state value has one owner. Inject explicit services such as view, post, and session getters through a small feature-specific factory argument rather than an unrestricted application context. Factories called after EditorView creation can close over the live view; startup-time extensions receive only callbacks they actually need. Do not instantiate a second editor or register handlers twice. Preserve window.app method names and signatures, native message payloads/load acknowledgment ordering, fromApp transaction annotation, browser-only storage fallback, selection-preserving reloads, capture-phase shortcut priority, and all command names. Keep document-input shortcuts from intercepting find/dialog fields and preserve native undo routing.

Update web/index.html dependency order so factories load before composition and existing Markdown/table/preview dependencies remain available. Update scripts/test.sh and scripts/test-webkit.sh syntax-check entry points to cover all newly loaded source scripts rather than only the old fixed list. Preserve bundled vendor dependencies and offline loading; no module-system migration or new runtime package is required. Risks are closure initialization order, globals accidentally captured before setup, duplicate event bindings, and document-token/revision ownership.

### S-5: Split live-preview widgets, decorators, and state orchestration

Move widget classes (image, bullet, rule, fence label, diagram, task checkbox) into preview-widgets.js. Extract inline decorators (emphasis, code, links/images/URLs, escapes/HTML) into preview-inline.js and block decorators (headings, lists/quotes/tasks, fenced/indented code, front matter, tables) into preview-blocks.js. Keep live-preview.js responsible for focused/pressed state, held mouse layout, tree traversal, shared decoration context, and the StateField providing decorations. If block decorators still exceed 50, separate list/quote decoration from code/table/block decoration by domain.

Pass an explicit decorator context with the current transaction state, line/selection predicates, decoration helpers, and list accumulation; use factory initialization for widgets. Preserve false returns that stop traversal into nodes, decoration sort order, the shared listLines map, table source-mode field, syntax-tree fallback, and the exported MarginLivePreview.extension/setFocused interface. Keep block widgets supplied by the existing StateField, not a view plugin, and retain mouse-down layout freezing until release. Update web/index.html and syntax-check scripts. Risks are marker hit testing, selection-layer order, focus simulation, and accidentally rendering child Markdown inside code blocks. Coordinate file moves with the separate prepared code-block-line-numbers task; this refactor does not implement that feature.

### S-6: Give table navigation an explicit movement value

Replace move(view, dom, cell, rowOffset, colOffset, addRowAtEnd) with move(view, dom, cell, movement), where movement has named rowOffset, colOffset, and addRowAtEnd fields. Use named movement values at the existing keyboard dispatch sites: forward Tab {0, 1, true}, backward Tab {0, -1, false}, Enter/ArrowDown {1, 0, false}, ArrowUp {-1, 0, false}. The braces here describe field values in that order; actual code uses named properties. Default omitted addRowAtEnd to false. Do not bundle unrelated arguments just to conceal them: the value represents one navigation request. Keep header/body indexing, horizontal wrap before vertical offset, top-boundary no-op, final-row creation only for forward Tab, and modifier-key bypass unchanged.

### S-7: Separate the table data model from widget interaction

Move parseRow/parseTable, cell escaping, coordinate-to-source helpers, and the edits object to table-model.js as one cohesive model/edit namespace. These functions produce CodeMirror-compatible change descriptions without mutating the editor or DOM. Move render/fillCell/startEditing/stopEditing and cell lookup to table-view.js, incorporating S-8. Keep sourceTables/showSource, apply, navigation, WidgetType integration, and event binding in table-editor.js. If the remaining controller still reaches 50, move contextual-menu construction into table-menu.js with explicit callbacks to edits and source-mode actions.

Preserve the public MarginTables.TableWidget/sourceTables interface used by live preview. Internal namespaces remain narrowly scoped and loaded in order through web/index.html. Keep apply's stale-source guard, edit-specific userEvent annotations, row/column focus requests, and mapped source-table positions. Model edits must retain escaped-pipe behavior, optional outer pipes, missing cells, alignment delimiters, and minimal edits for cell input. Risks are import/load order, cycling dependencies between view and controller, and source offsets changing when a table precedes another table. View code receives the minimum edit callback where needed; it must not import the controller back.

### S-8: Make render's caret-preserving and rebuild paths explicit

Keep render as a short coordinator: parse current source, store dom.tableSource, compute shape and active cell, then either refresh nonediting cells and return or rebuild the table and restore requested focus. Extract refreshOtherCells, buildTableElement, and restoreFocus with one responsibility each. Capture the previous active-cell coordinates before replacing children; consume focusAfterRender exactly once; clamp focus using the existing header/body coordinate rules.

The same-shape editing path must retain the exact contenteditable DOM node and its native selection, including any uncommitted text. Do not replace the table on every input, fill the active cell, or call focus while the user is already editing it. Structural changes may rebuild and then restore the requested clamped cell. Update tableShape/tableSource consistently on both paths. The critical acceptance evidence is node identity and caret behavior, not just identical generated HTML. Extracted functions also need to remain below Qlty's complexity threshold.

### Implementation sequence

Use separate reviewable slices: S-6 and S-8 first (small table behavior contracts), then S-7 (table boundaries), S-5 (preview boundaries), S-4 (editor composition), S-3 (sidebar), S-1 (window coordination), and S-2 last (native composition). The order reduces overlapping edits and establishes conventions before the broad native split. Each slice must keep the application buildable and tests passing; S-6/S-8 may share one change because they touch the same widget. Measure after each extraction and choose the documented fallback split only when needed. Before changing Swift files, account for private access across new files through owned collaborators or narrowly scoped internal methods. Keep AppKit selectors, state ownership, and observer teardown visible to reviewers.

## Non-goals

- Implementing the refactors or changing application behavior during this proposal task.
- New editor features, visual redesign, changes to Markdown format, native message protocol, persisted restoration keys, undo semantics, or dependencies.
- Raising Qlty thresholds, adding suppressions/exclusions, renaming functions to evade findings, or reducing counts by collapsing readable logic into opaque expressions.
- Fixing unrelated Qlty check findings or scanning tests with --include-tests; the target inventory is the current default all-files smells scan. Any separate security/configuration finding should be reported separately.
- Preparing this draft through independent critique or publishing issues unless separately requested.
